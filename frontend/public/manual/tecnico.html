1Visión general

NicheRadar AI es una aplicación local de cinco servicios que se ejecutan en contenedores Docker. Una base de datos PostgreSQL guarda todo; una API FastAPI la expone; un worker ejecuta las tareas largas; una interfaz React la muestra.

Principio de diseño Ningún request HTTP espera una tarea larga. Las búsquedas y los cálculos se encolan en la base y el worker los ejecuta. Un cero nunca sustituye a un dato faltante: los campos sin dato son NULL.

3Requisitos

  • Windows 10 u 11 con Docker Desktop y motor WSL 2 activado.
  • Docker Desktop con Compose v2 o superior (probado con Docker 29.9.2 y Compose v5.6.1).
  • Git (para trabajar con el repositorio).
  • Recursos: al menos 8 GB de RAM asignados a Docker. Puertos libres: 15432, 8000 y 5173.
  • No hace falta Python ni Node en el equipo: todo corre en contenedores.
Dropbox El repositorio puede estar en una carpeta sincronizada. Dropbox puede bloquear archivos mientras Docker escribe. Si aparecen errores intermitentes de escritura, mueva el proyecto fuera de Dropbox.

4Configuración

La configuración llega a los servicios por tres vías, en este orden de prioridad:

  1. Variables de entorno del proceso que ejecuta Compose (por ejemplo, la variable de usuario de Windows).
  2. El archivo .env en la raíz del proyecto. No se versiona.
  3. Los valores por defecto de backend/app/core/config.py.

No versionar secretos .env está en .gitignore. Las claves deben vivir en la variable de usuario de Windows o en el .env local, nunca en el repositorio.

Cómo leer una clave desde PowerShell sin mostrarla

$env:YOUTUBE_API_KEY = [Environment]::GetEnvironmentVariable('YOUTUBE_API_KEY','User')
[bool]$env:YOUTUBE_API_KEY   # devuelve True o False, nunca el valor

5Arranque

Desde PowerShell, en la carpeta del proyecto (o con --project-directory desde cualquier carpeta). En los comandos de este manual, <ruta> es la carpeta del proyecto, por ejemplo C:\Luis\Dropbox\Negocios\202608_Youtube\2026\NicheRadar_AI_Claude_Code\NicheRadar_AI.

  1. Pasar la clave de YouTube a Compose (solo si va a buscar en YouTube). 
    $env:YOUTUBE_API_KEY = [Environment]::GetEnvironmentVariable('YOUTUBE_API_KEY','User')
  2. Levantar el stack y construir las imágenes. 
    docker compose --project-directory "C:\Luis\Dropbox\Negocios\202608_Youtube\2026\NicheRadar_AI_Claude_Code\NicheRadar_AI" up -d --build
  3. Esperar a que la base esté sana y la migración termine con código 0. 
    docker compose --project-directory "<ruta>" ps
docker compose --project-directory "<ruta>" logs migrate
  4. Comprobar la salud de la API. 
    Invoke-RestMethod http://127.0.0.1:8000/health/ready

    Debe responder status: ready.

  5. Abrir la aplicación. Interfaz en http://localhost:5173, documentación de la API en http://127.0.0.1:8000/docs.
Arranque sin clave Si no define YOUTUBE_API_KEY, todo funciona salvo las búsquedas en YouTube, que responden 409 PROVIDER_NOT_CONFIGURED.

Reiniciar un servicio después de cambiar configuración

Los cambios en variables de entorno requieren recrear los contenedores que las usan:

docker compose --project-directory "<ruta>" up -d api worker

7Pruebas

Todas las pruebas corren dentro de contenedores, sin red externa. La suite de integración usa la base nicheradar_test, que se recrea en cada sesión, y fija su propia configuración (restricted), así que no depende del .env local.

# Backend: unitarias e integración
docker compose --project-directory "<ruta>" run --rm --no-deps api pytest -q

# Backend: estilo y tipos
docker compose --project-directory "<ruta>" run --rm --no-deps api sh -c "ruff check app tests && ruff format --check app tests && mypy app"

# Frontend: lint, tipos y pruebas unitarias
docker compose --project-directory "<ruta>" run --rm --no-deps frontend sh -c "npx eslint . && npx tsc --noEmit && npx vitest run"

# E2E de navegador (requiere el stack arriba)
docker compose --project-directory "<ruta>" --profile e2e run --rm e2e

Resultado de referencia: 265 pruebas de backend, 23 de frontend y 9 E2E pasando, con 1 E2E omitido a propósito (la comprobación de desbordamiento solo corre en móvil).

9Trabajos y worker

Cada corrida crea una fila en research_runs y una tarea en run_tasks. El worker reclama tareas con FOR UPDATE SKIP LOCKED, así dos workers nunca toman la misma.

Qué tipos de tarea existen

TipoLo lanzaQué hace
demo_researchCorrida DEMOResume el dataset sintético. Sin red.
youtube_discoveryBúsqueda en YouTubeEjecuta consultas por idioma y ventana. Guarda el progreso por consulta.
spanish_planGenerar plan con IAPide el plan al proveedor, lo valida y lo guarda como pendiente de revisión.
spanish_validationValidar en españolBusca cada frase del plan aprobado y recalcula la evaluación.
vidiq_discoveryCorrida vidiq (API)Consulta outliers a vidIQ por MCP, con tope de créditos y compuerta vidiq_api. Guarda videos como PROVEEDOR con caducidad de 29 días.
retention_purgeCorrida purge (API)Expira datos de terceros fuera de plazo.

Una búsqueda que se pausa por cuota conserva las consultas completadas en run_tasks.result_json. Al reanudar, solo se ejecuta lo pendiente.

Ejemplo: lanzar una búsqueda

$body = @{ kind='discovery'; payload=@{ queries=@(@{ language='es'; query='historia con mapas'; window='8-30' }); max_search_calls=1; pages_per_query=1 } } | ConvertTo-Json -Depth 6
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/research-runs -ContentType 'application/json' -Body $body

Responde 202 con el id de la corrida. Consulte su estado con GET /research-runs/{id}.

11Compuerta de políticas

Las capacidades condicionadas (advanced_scores, derived_metrics, extended_history, vidiq_api) solo se abren si se cumplen las tres condiciones:

Las aprobaciones se registran solo por línea de comandos (app.jobs.policy_cli), con referencia documental, revisor y fecha de caducidad obligatorias. No existe ruta de la API ni pantalla que las conceda.

Estado en este equipo Las cuatro capacidades tienen una aprobación registrada por el responsable (decisión D-54 en docs/DECISIONS.md). El modo está en approved_scope por el .env local. Esta aprobación no es una autorización emitida por YouTube.

12Cuota y retención

Cuota

  • search.list cuesta 100 unidades. videos.list, channels.list y playlistItems.list cuestan 1 unidad por llamada.
  • El día de cuota empieza a medianoche de Pacific Time (quota_service.quota_day_start).
  • Cada llamada se reserva antes de enviarse. Si no cabe en el presupuesto blando, la tarea pasa a PAUSED_QUOTA.
Diferencia con la especificación La especificación (§5.2) habla de 1 unidad por search.list. La documentación oficial dice 100. El código usa 100. Confirme la cuota real del proyecto en Google Cloud Console.

Retención

Los datos de terceros (API o importaciones) se guardan con owner_authorized=false y retention_deadline a 29 días. Un expirado se purga con kind=purge: los valores quedan en NULL, el título pasa a «[Dato caducado]» y el registro se marca EXPIRED. La purga todavía no corre sola (M5).

15Límites y decisiones

  • Sin fuente de demanda con licencia. Ninguna oportunidad pasa de «demanda no demostrada» con datos reales (D-35).
  • IA sin probar contra APIs reales. Los adaptadores están probados con transporte simulado. Algunos modelos de razonamiento pueden rechazar temperature=0 (D-47).
  • Índices cerrados por falta de datos. La resiliencia temporal requiere un histórico licenciado; sin él, los índices integrados quedan en NULL (D-50).
  • Pendientes de producto. Scheduler automático y purga programada (M5), watchlist, detección de canales espejo y revisión humana de 30 a 50 videos para medir precisión. Lista completa en docs/HANDOFF.md.
  • Banner por modo de datos. GET /config/public devuelve data_mode (SYNTHETIC, MIXED o REAL) y la interfaz muestra la etiqueta correspondiente (D-59).
  • Sin autenticación. La API y la interfaz solo se deben exponer en 127.0.0.1.
  • Datos de demostración en la base. syn-opp-06 mezcla un video real con datos sintéticos.
  • Proceso manual. Anotaciones, importaciones, purgas y aprobaciones son acciones de administración, no pantallas.

Las decisiones completas están en docs/DECISIONS.md, y el estado de cada hito en docs/IMPLEMENTATION_PROGRESS.md. Para retomar el trabajo en una sesión nueva, lea docs/HANDOFF.md.
